Plain Council: Municipal Readiness Report

Plain-language, source-linked summaries of council items, approved by a person before publishing. CIVIC Hack 2026 · Live prototype: plain-council.vercel.app · Tested on 3 real Toronto items (2 decided, 1 open for comment)

1. Who would use it

  • Residents, especially renters, newcomers, students, seniors and shift workers. No account needed. They enter the first 3 characters of a postal code (or pick a ward) and get a card for each item: what is proposed or decided, who and where it affects, what changed at each step, and whether they can still comment.
  • City Clerk's Office / engagement staff run one script per item and approve, edit or reject each AI-drafted sentence in a simple review screen. Every action is logged with who and when.
  • Councillors' offices, libraries, community groups, media share card links. Every sentence links to the exact source passage.

2. Data and resources needed

  • Data the City already publishes: meeting-site item pages and staff reports, Council Voting Record, Report Request Log, ward boundaries. Also Statistics Canada postal-area boundaries. Nothing new has to be collected.
  • People:
    • One reviewer: about 15 minutes per item (10–20 minutes in testing).
    • One IT contact: about 2 days to set up, then about 2 hours a month.
  • Systems: a Postgres database (Supabase), web hosting (Vercel) and an AI model provider. All are swappable for systems the City already uses.

4. Privacy

  • Postal code. Only the first 3 characters (an area, not a home) are used. They're matched against a file in the website, and never stored or sent anywhere.
  • Nothing about residents reaches the AI. It only reads public City documents, once, before publishing.
  • People who wrote in or spoke are counted, never named or summarized. Their names are kept out of the database and the code.
  • Accounts. No resident accounts and no tracking. Staff accounts are created by an administrator; public sign-up is off.
  • Security. Database rules let the public read approved sentences only. Nobody can edit a sentence's source quote. AI and admin keys never reach the website.

5. What residents should know

  • This is a summary, not the official record. If they differ, the official record is correct. Every sentence links to its source.
  • AI drafts the sentences and a person approves each one. The card shows the date it was checked.
  • Tags show the step: a staff or committee recommendation is not a final decision.
  • Deadlines. A comment deadline is shown only if the City's page states it. Check the official page before you submit.
  • Wards. A postal area can cross ward lines. Confirm your ward with the City's address finder.

6. How other municipalities could adapt it

  • One reader to replace. Only the meeting-site reader is Toronto-specific. A city on eSCRIBE, Granicus or iCompass writes one reader that returns the same fields: items, steps, decision text, documents. Checks, review screen and website stay the same.
  • Ward lookup. Rebuild it from the city's own ward boundaries with the included script.
  • AI model. The model is one setting. An open-weight model can run on the city's own servers if procurement requires it.
  • Documented. Setup steps, tests (62) and architecture documents are in the repository.

7. Suggested pilot

  • Scope: 3 months, one committee or community council.
  • Reviewer: a clerk who did not build the tool reviews each card.
  • Measure:
    • corrections per card (testing: 27 of 62 sentences reworded and 6 rejected before publishing)
    • time to publish
    • visits by ward
    • clicks to the City's comment form
  • Then: add translation and a printable poster for libraries and tenant groups.
